# Vendor / Outbound Integration Conventions

Applies only to a domain whose `CommandExecutor`/`QueryProcessor` calls an external
vendor system (OTA, payment gateway, or any third-party HTTP API) rather than only
reading/writing this service's own database. Most CRUD-only domains generated by
`be-crud` never need this file — read it only when a `{domain}/client/` package is
being added.

This template exists because the CQRS package structure in `CLAUDE.md` and the data
patterns in `templates/entity-conventions.md` are both scoped to this service's own
database. Neither one answers what happens when the thing on the other end of a call
is not this service's own transaction — a vendor call **will** fail, and the only
open question is when and who is left holding a state mismatch. Every rule below
exists to answer that question in advance, not after an incident.

## Package Placement

```
{domain}/
├── api/                         <- inbound (see CLAUDE.md CQRS package structure)
├── client/                      <- outbound vendor calls, this file
│   └── {Vendor}Client.java      <- book() / retrieve() / cancel(), one per vendor
├── {Description}Exception.java
└── {Entity}PropertyValidator.java
```

A `{Vendor}Client` is never a repository or mapper — do not put it in `data/`. It is
also never called from inside a `TransactionalOperator`-wrapped `Mono` (see
`docs/decisions.md` Decision 7 addendum) — a network call must not hold a DB
transaction's row locks open for its duration.

## Naming

| Type | Pattern | Example |
|------|---------|---------|
| Vendor client | `{Vendor}Client` | `AcmeClient`, `GlobexClient` |
| Vendor call methods | `book` / `retrieve` / `cancel` | `acmeClient.book(command)` |
| Circuit breaker name | `{vendor-id}` (lowercase, matches the vendor's own key) | `"acme"`, `"globex"` |

## Timeout — two independent guards, never one

A vendor call needs **both** of these, not either/or:

1. **Connect-timeout and read-timeout set separately** on the `WebClient`'s
   underlying `HttpClient` (Reactor Netty) — a slow DNS/TCP handshake and a vendor
   that accepts the connection but never responds are different failure modes and
   should not share one timeout value.
2. **`.timeout(Duration)` on the reactive chain itself**, wrapping the
   `client.book(...)` call, independent of the HTTP client's own timeout — this is
   the guard that fires if the HTTP client's timeout is misconfigured or absent,
   and it is what makes the failure visible to `StepVerifier`/tests in the same way
   any other timeout is.

**This service's own timeout must be shorter than whatever calls it** (e.g.
`queue-api` or another upstream caller's timeout). A vendor timeout longer than the
caller's timeout does not make the call safer — it just means the caller gives up
and moves on while this service is still holding the request open, silently wasting
the connection/thread it occupies.

If the target project uses an AOP method-timing convention (e.g. a `@TimeTrace`-style
annotation logging any method over a fixed threshold), use that threshold — not this
plugin's own guess — as the mark for "the vendor is slow" in review discussions; this
plugin does not define or ship such an annotation itself. A `{Vendor}Client` call
regularly landing near or past that mark is a signal to look at the circuit
breaker's slow-call-rate threshold, not just the raw timeout duration.

```java
webClient.post().uri(bookingUri)
    .bodyValue(vendorRequest)
    .retrieve()
    .bodyToMono(VendorBookingResponse.class)
    .timeout(Duration.ofSeconds(8))
    .transformDeferred(CircuitBreakerOperator.of(circuitBreaker));
```

## Retry — only for idempotent operations, never blind

**`book()` (create) is never blind-retried.** A booking/create call has no
idempotency guarantee unless the vendor's own API explicitly documents an
idempotency key — if it does not, do not retry `book()` at all; treat an ambiguous
failure as a case for reconciliation (see below), not a case for "try again."

`retrieve()` and `cancel()` are typically safe to retry — they are read/re-assert
operations keyed by the vendor's own booking reference, not creates — but still need
all three of these together, never retry alone:

- **Backoff + jitter**: `Retry.backoff(maxAttempts, minBackoff).jitter(0.5)` —
  never a fixed-interval retry. A vendor already struggling under load gets a
  synchronized retry storm from every caller if the retry interval is uniform; this
  is self-inflicted DDoS against a vendor that is already the weak point.
- **A hard cap on attempts** — `maxAttempts`, not an unbounded retry loop.
- **A retry filter that excludes 4xx**: a 4xx response means the request itself was
  rejected (bad request, unauthorized, not found) and will fail identically on
  retry — only retry on timeout, connection-reset, or a 5xx that the vendor's own
  contract documents as transient.

```java
vendorClient.retrieve(bookingRef)
    .retryWhen(Retry.backoff(3, Duration.ofMillis(500))
        .jitter(0.5)
        .filter(VendorIntegrationTemplate::isRetryable))
    .timeout(Duration.ofSeconds(5));

private static boolean isRetryable(Throwable e) {
    if (e instanceof VendorClientException vce) {
        return vce.statusCode() == null || vce.statusCode().is5xxServerError();
    }
    return e instanceof TimeoutException || e instanceof ConnectException;
}
```

## Ambiguous Timeout — reconcile via `retrieve()`, never assume

If `book()` times out or the connection resets, **this service does not know
whether the vendor received and processed the request.** Treating that as "booking
failed" is a guess, and it is the exact mismatch this file exists to prevent: the
vendor may have created the reservation while this service believes it did not.

The rule: on an ambiguous outcome from `book()`, the CommandExecutor calls
`vendorClient.retrieve(...)` to ask the vendor directly what it actually did, and
only then decides the local state. Never resolve an ambiguous `book()` outcome by
retrying `book()` itself — that risks a second, duplicate reservation instead of an
answer.

```java
public Mono<Void> execute(CreateBooking command) {
    return vendorClient.book(command)
        .flatMap(this::persistConfirmed)
        .onErrorResume(this::isAmbiguous, e -> vendorClient.retrieve(command.reference())
            .flatMap(state -> switch (state.status()) {
                case CONFIRMED -> persistConfirmed(state);
                case NOT_FOUND -> Mono.error(new BookingFailedException(command.reference()));
                case PENDING -> Mono.error(new BookingReconciliationRequiredException(command.reference()));
            }));
}

private boolean isAmbiguous(Throwable e) {
    return e instanceof TimeoutException || e instanceof ConnectException;
}
```

A `PENDING` result from `retrieve()` is not resolved by guessing either — surface it
as its own exception/state so it is retried by a reconciliation job, not silently
collapsed into success or failure.

## Cancel — never mark local state cancelled before the vendor confirms

Symmetric to the booking case: a cancel command must only update this service's
record to "cancelled" **after** `vendorClient.cancel(...)` returns a confirmed
success. If the vendor call fails or times out, leave the local record in a
"cancellation pending" state (not cancelled, not active) for reconciliation —
never let a failed vendor call still result in a local "cancelled" write. Marking
cancelled on a failed vendor call is the direct path to a state mismatch where money
is lost: the user believes the reservation is gone, the vendor still holds it.

```java
public Mono<Void> execute(CancelBooking command) {
    return vendorClient.cancel(command.reference())
        .flatMap(result -> bookingRepository.markCancelled(command.reference()))
        .onErrorResume(this::isAmbiguous,
            e -> bookingRepository.markCancelPending(command.reference()));
    // markCancelPending, not markCancelled -- a reconciliation job resolves it later
}
```

## Circuit Breaker — one instance per vendor, never one shared instance

Resilience4j 2.1.0 `CircuitBreaker` instances are keyed by vendor id (`"acme"`,
`"globex"`, etc.), configured independently. **Never share one `CircuitBreaker`
configuration across multiple vendors** — one vendor having a bad day opens the
breaker for every vendor sharing it — one bad vendor dragging down the threshold for
the whole cluster is a known failure mode, not a hypothetical one.

State the fallback behavior explicitly per call site, because it differs by shape:

- **Fan-out search across N vendors**: an open breaker for one vendor means that
  vendor is excluded from the result set, not that the whole search fails. Log it,
  continue with the remaining vendors.
- **Single-vendor operation** (book/cancel a specific reservation with a specific
  vendor): an open breaker means the caller gets a specific "vendor temporarily
  unavailable" domain exception, distinguishable from a generic 500 or from "vendor
  rejected the request."

## Fan-out to Multiple Vendors — bounded concurrency, isolated failures

A search across N vendors is a `Flux`/`flatMap` fan-out, and it must not be
unbounded — an uncapped `flatMap` across many vendors competes for the same
connection pool and `boundedElastic` threads that single-vendor request paths are
also drawing from (see `skills/be-data/SKILL.md` rule 2 for the equivalent DB-side
hazard). Cap concurrency explicitly:

```java
Flux.fromIterable(vendors)
    .flatMap(vendor -> vendor.search(query)
        .onErrorResume(e -> {
            log.warn("vendor {} search failed, excluding from results", vendor.id(), e);
            return Mono.empty();
        }), /* concurrency */ 8)
    .collectList();
```

`onErrorResume(... -> Mono.empty())` here is deliberate and scoped to the fan-out
result, not a silent swallow — the error is logged, and only *that vendor's*
contribution is dropped. One vendor's failure must never null out the whole search
result for the user.

## Response Normalization at the Adapter Boundary

Parse a vendor's response into this service's internal DTO **inside** `{Vendor}Client`
— never let a raw vendor field (a different currency, a vendor-local timezone, a
vendor-specific room/fare code) leak past the client class into `commandmodel`/
`querymodel`. Normalize currency and timezone (to this service's own UTC + minor-unit
convention) at the point of parsing, not downstream — downstream code should never
need to know which vendor a value came from.

## Price/Availability Cache — never book directly off a stale cache read

Vendor price/availability responses are cached with a 10-minute TTL. A `book()` call
must not use that cached value as-is to decide to book — the vendor may reject the
booking or return a different price at booking time. Either revalidate availability
immediately before `book()`, or rely on the vendor's own booking-time validation and
handle a price-mismatch response as its own domain exception (not a generic booking
failure) so the caller can show the user a real repricing decision instead of an
opaque error.

## Logging

Never log a raw vendor request/response payload verbatim if it may contain card or
guest PII — mask or omit those fields before logging. This template does not judge
what counts as sensitive; if a payload's sensitivity is unclear, treat it as
sensitive and hand off to the security-focused review rather than guessing.
